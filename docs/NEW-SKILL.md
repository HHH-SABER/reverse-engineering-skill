# 新增一个技能

## 三步

```bash
# 1. 复制骨架
cp -r skills/_template skills/my-new-skill

# 2. 改名（目录名与 frontmatter name 必须一致）
#    编辑 skills/my-new-skill/SKILL.md 的 name 与 description

# 3. 在 CATALOG.md 的「技能清单」表里加一行
```

然后自检。

## 填 `SKILL.md` 的 frontmatter

```yaml
---
name: my-new-skill          # kebab-case，必须与目录名一致
description: >-             # 关键。写清「什么时候该用它」，不是「它是什么」
  用一句话说明触发条件 + 能力边界。列出具体关键词，便于运行时路由。
metadata:
  version: "0.1.0"
---
```

`description` 是**唯一的路由依据**——写"这是一个关于 X 的技能"没用，要写"当用户要做 X / 遇到 Y 报错 / 需要 Z 时使用"。同时也写清**不负责什么**，把其它领域路由出去。

## 正文怎么写

| 段落 | 作用 |
|---|---|
| `## 先判断：这个任务归谁` | 路由表。什么都不做之前先分流，避免和其它技能重复 |
| `## 使用边界` | 合规声明。不协助的领域要明确列出 |
| 主体各节 | 步骤 / 检查表 / 决策树。**可执行**，不是知识陈述 |
| `## 维护` | 源真身在哪、改完跑什么、怎么回归测试 |

## 自检清单

- [ ] 目录名 == `frontmatter.name`，且是 kebab-case
- [ ] `SKILL.md` 在目录**根部**（运行时只认 `<root>/<name>/SKILL.md`，一层深）
- [ ] `description` 写的是触发条件，不是能力描述
- [ ] 写清了**不负责什么**，并把那些领域路由到具体技能
- [ ] `CATALOG.md` 已加一行，代号取自**受控词表**（没有合适代号就先填 `misc`）
- [ ] `CHANGELOG.md` 已记首版
- [ ] 正文与脚本里**没有本机绝对路径**（用 `<corpus-root>` / 环境变量占位）
- [ ] 正文与脚本里**没有凭据**（token / key / 密码 / 私有 URL）
- [ ] 不依赖私有语料也能加载（缺语料时应提示并询问，而不是静默失败）
- [ ] 如果引用了语料，`CATALOG.md` 的「依赖语料」列已填

## 提交信息

```
feat(skills): 新增 <skill-name>

- 职责：<一句话>
- 分类：<cat>
- 依赖语料：<none | 名称>
```

改动既有技能用 `fix(skills): <name> — <改了什么>`，收窄/删内容用 `refactor(skills): <name> — <为什么>`。

## 什么时候该新建技能，而不是加进现有技能

新建：

- 有独立的触发场景（用户会单独想到它）
- 需要自己的 `references/` 或 `scripts/`
- 现有技能的 `description` 塞进这个能力后会变成"什么都做"的模糊描述

不新建：

- 只是现有技能的一条新规则 → 加进对应段落
- 只是一份领域知识表 → 放现有技能的 `references/`
- 只是现有技能的变体参数 → 做成配置项

> 判断标准：**两个技能会不会被同一个任务同时用到？** 会 → 说明它们该合并；不会，且各有独立触发条件 → 该分开。
